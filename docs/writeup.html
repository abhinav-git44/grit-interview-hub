GRIT Interview Hub — Interview Scheduling & Badge Lifecycle

AI Product Engineer · Round 1 · Abhinav Chaudhary
November 2026 · prototype + Supabase/PostgreSQL backend

One journey per student × badge level (Novice, then Master), because each level has its own interview. Each dimension is stored separately: eligibility (computed from skills, never a flag), booking, attendance, interview, outcome, badge and malpractice case. The state the student sees is derived from those, so it can never contradict them.

Assumptions, data model & governance

GRIT Interview Hub · Round 1

4Product assumptions

GIVEN BY THE BRIEF

  • Interview unlocks when every required skill for the Track Badge is cleared.
  • Small interviewer team, each with own availability; students book from their dashboard.
  • Outcomes: Pass, Fail, Retake later. Pass earns the badge.
  • Ops see which eligible students have booked and which have not.
  • A badge can be nullified if malpractice is flagged later.

MY ASSUMPTIONS — all editable by ops, all audited

  • 30-min interviews, 10-min buffer; book 2 h–21 days ahead; change until 12 h before (max 2 reschedules).
  • Retake later = 5-day cooldown (mirrors GRIT's 5-day re-attempt gap); Fail = 14 days; 3 counted attempts per badge.
  • Student no-show counts as an attempt (3-day cooldown); interviewer no-show or cancellation never does.
  • Interviewers correct non-Pass results within 24 h; ops after. Only reviewers decide malpractice.
  • Open questions: Fail vs Retake semantics · attempt limit · appeal window · does a nullified Novice void Master?

5Database schema & entity relationships — PostgreSQL / Supabase, 3 migrations, 20 tables

6Booking concurrency protection

  • Serialise: book_slot() takes an advisory lock per student × badge, then SELECT … FOR UPDATE on the slot — concurrent requests queue, then re-check status.
  • Re-validate inside the lock: eligibility, cooldown, attempts, notice, horizon, interviewer active, the student's other bookings.
  • Backstop: partial unique indexes (one active booking per slot; per student × badge) and GiST exclusion (no overlapping slots per interviewer).
  • Idempotent: a retried request with the same key returns the original booking. Reschedules lock both slots in id order — no deadlocks.
  • Atomic: slot, booking, attempt, audit and notification commit together or not at all.

7Malpractice & badge governance

  • Flag ≠ decision. Ops, or an interviewer who interviewed that student, may flag. The badge moves to Under review and stays visible to the student, with neutral wording.
  • Decide: only reviewers (can_review_malpractice). Confirm requires an open investigation and a ≥ 15-char reason; the student is told the outcome, never the evidence.
  • Never delete: nullification is a status change; earned_at, badge events, case timeline and audit rows are append-only (triggers).
  • Defence in depth: anon has no access; signed-in users only SELECT through RLS; every write is a SECURITY DEFINER RPC that checks the caller from auth.uid(), with pinned search_path.
